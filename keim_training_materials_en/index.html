0. Preface: The Genesis of Keim

The vision

Keim was designed as a sovereign programming substrate: readable enough for training, close enough to the machine to reason about runtime, memory, native execution and delivery artefacts. The course therefore teaches syntax, but also system thinking: values, state, rules, fields, agents, modules and runtime boundaries.

Why the name “Keim”?

A keim, a seed or germ, is a compact unit that contains a plan for growth. A small Keim program can start with a few named values and grow into an HTTP service, a field simulation, a Web adapter, a native target or a runtime package.

Path to v4.3.3 and beyond

The original v4.3.3 course remains the foundation. Later v7.5 Enterprise chapters add stable bytecode, Result/Match, Web/WASM, security and hardening. Version v7.8.5 adds the delivery layer: full runtime packaging, self-bootstrapping launchers, GPU-aware packaging and verifiable bundles.

After this training learners should be able to write Keim programs, inspect their state model, expose simple HTTP APIs, understand runtime artefacts and package a program for controlled delivery.

2. The Keim mental model

Programming as a state machine

Keim treats a program as controlled state transitions. Values are created, checked, transformed and emitted. This is useful in simulations, APIs and training because every step can be explained as an explicit change.

Key terms

TermMeaning
memory / SpeicherA named storage location with a type and a value.
fieldA computed space, grid or influence layer used by agents or simulations.
tracePersistent or temporary evidence left by agents or rules.
agentAn entity that carries state and acts according to rules.
runtimeThe execution layer that interprets, compiles, packages or hosts the program.

6. Syntax basics

6.1 Comments

Comments explain intent and are ignored by the runtime.

6.2 Indentation

Blocks are visually structured. Wrong indentation is one of the most common beginner errors.

6.3 Declarations and actions

Declarations introduce state. Actions change or use state.

6.4 Names

Use clear names. The language intentionally supports readable German keywords, but the programming concepts are universal.

7. Values and types

A type defines what operations make sense for a value.

Typed memory

Types reduce ambiguity and make runtime validation, bytecode stability and packaging metadata easier.

8. World, fields, traces and agents

8.1 World

The world is the container for simulation state.

8.2 Fields

Fields store spatial or logical influence values. They are useful when many agents react to shared gradients instead of direct object-to-object calls.

8.3 Field calculation

A field can be updated each tick, diffused, decayed or recomputed from agent positions.

8.4 Traces

Traces are signals left by actions: heat, scent, cost, visited positions or debugging markers.

8.5 Create and delete agents

Agents carry local state. Deletion must be explicit or controlled by lifecycle rules to avoid invisible state leaks.

9. Memory and collections

9.1 Change memory

9.2 Read aggregations

Aggregations summarize lists, maps, tables or fields.

9.3 Lists

Lists preserve order and are useful for queues, paths and batches.

9.4 Maps

Maps connect keys to values and are essential for JSON-like data, configuration and lookup tables.

Why maps matter

Maps are the bridge between readable data and structured program state.

10. Control flow

10.1 Every round

Repeated rules model ticks, frames or service loops.

10.2 Conditions

Conditions decide whether a block runs.

10.3 One-line conditions

Short checks are useful, but complex logic should remain expanded for teaching.

10.4 Rules

Rules connect a condition with an action and make simulations explainable.

10.5 Periodic blocks

Periodic blocks run at controlled intervals.

10.6 Events

Events decouple causes from reactions and are useful for APIs, UI and agent systems.

11. Functions, values, blocks and modules

11.1 Functions

Functions group reusable logic. They should receive input, compute a result and avoid hidden side effects where possible.

11.2 Built-in expression functions

Built-ins cover common tasks such as text, math, paths, JSON and time.

11.3 Values

Values are transported through expressions, function calls, modules and runtime boundaries.

11.4 Blocks

Blocks form named regions of behavior and are useful in training because they can be tested separately.

11.5 Imports

Imports make modules reusable and keep large programs understandable.

12. Classes, objects, inheritance and GC

12.1 Define a class

A class describes the fields and behavior of similar objects.

12.2 Create an object

An object is a concrete stateful instance.

12.3 Inheritance

Inheritance reuses structure, but should not hide state transitions from learners.

12.4 Dynamic objects

Dynamic objects are flexible, but require stronger validation.

Why GC?

Garbage collection prevents unused heap objects from growing without bounds. Keim uses GC topics to teach practical memory lifecycle thinking.

16. Error handling

Error handling turns failure into structured data.

What is caught?

Parsing errors, type mismatches, missing files, invalid requests and runtime exceptions can be converted into controlled responses.

Good API error responses

18. Native VM, SoA and performance

18.1 Why a native VM?

A native VM can reduce Python dispatch cost and object allocation overhead.

18.2 SoA instead of AoS

Structure-of-arrays layout improves cache behavior when many agents are processed in batches.

18.3 Build the native VM

The build is optional in the course and depends on the local toolchain or internal native linker path.

18.4 GPU driver bridge

The GPU bridge is treated as a controlled extension point: it must have a manifest, smoke test and CPU fallback in v7.8.5 packaging.

23. Keim v7.5 Enterprise: what changed since v4.3.3

v7.5 keeps the original training model but adds enterprise-grade runtime concepts: stable bytecode, a clearer value model, Result/Match, Web/WASM targets, capabilities, SBOM and hardening.

24. Current Keim architecture as a learning model

The architecture can be taught as a chain: source → parser → semantic analysis → bytecode/runtime model → interpreter/native/WASM execution → tests → package → verification.

Why this chain matters

It gives learners a map from a line of source code to a deliverable artefact and shows where errors, security checks and performance decisions enter.

25. KBC-STABLE-1: stable bytecode as training anchor

KBC-STABLE-1 gives the course a stable intermediate representation. Learners can compare source-level intent with runtime-level operations.

Example

A typed value declaration becomes a value allocation plus metadata. That makes type errors, package manifests and bytecode tests easier to explain.

26. Result, Match and type thinking

Result values make success and failure explicit instead of hiding them in ambiguous exceptions.

Didactic flow

  1. Show a failing operation.
  2. Wrap it as result_ok or result_error.
  3. Use Match to branch on the result shape.
  4. Explain why this improves APIs and runtime verification.

27. Records, lists, maps and WASM heap

Domain view

Records describe structured entities, lists model order, maps model keyed lookup.

Runtime view

In a heap runtime, these values need handles, tags, allocation rules and eventually garbage collection.

28. Memory management: region, hashmap, GC and compaction

Keim uses memory management topics to show why high-level values still need low-level lifecycle rules. Region allocation is fast for short-lived groups. Hashmaps support dynamic lookup. GC recovers unused objects. Compaction improves locality but can invalidate raw references if not handled carefully.

29. Native and WASM: compare three execution paths

PathBenefitRisk
Python referencePortable and debuggable.Higher dispatch and object costs.
NativeLower overhead and platform integration.Build, ABI and safety complexity.
WASMSandboxed and browser-friendly.Interop and heap-model complexity.

30. Enterprise security: capabilities, SBOM and reproducible builds

Capabilities restrict what a program may access. SBOM documents included components. Reproducible builds make artefacts auditable. In training, these concepts are framed as engineering discipline, not bureaucracy.

31. Web training: DOM, import maps and JS interop

The Web path shows how Keim concepts meet browser artefacts. Import maps define module resolution, JS adapters form the boundary to the browser, and DOM interaction must stay explicit to remain teachable.

32. Training Impossible: prototype for self-optimisation

The Training Impossible prototype demonstrates how a system can record attempts, compare outputs and improve workflows. It should be taught carefully: self-optimisation requires testable goals and guardrails.

What learners understand

Feedback loops are only useful when measurements, constraints and rollback rules are clear.

33. Hardening Matrix: professional checks instead of hope

The hardening matrix collects checks for runtime, platform, security, tests, packaging and documentation. It turns “it works on my machine” into a structured release decision.

35. Keim v7.8.5: Self-Bootstrapping Runtime Packager

35.1 What is new

v7.8.5 adds a delivery layer. A Keim program can be packaged with its runtime, manifest, launcher scripts, optional Web overlay, GPU driver plan and verification metadata. The goal is not merely to run source code, but to deliver a checkable runtime bundle.

35.2 Four packaging modes

ModeUse
full-runtimeBundle the full runtime for maximum compatibility.
native-subsetUse a smaller native-oriented subset where supported.
zipappSingle-file Python zip application for simple distribution.
directory-bundleReadable folder layout for training, debugging and inspection.

35.3 Package structure as training model

A package contains runtime files, launcher, manifest, program source or bytecode, optional GPU material, verification report and Web overlay. Each part answers one question: what is executed, how is it started, what is included, and how can it be checked?

35.4 Central commands

python -m keim exe-status --json
python -m keim exe-pack examples/agenten_zweige_v78_1_gpu_aware/src/main.keim --out build/agenten_bundle --name agenten_zweige --target auto
python -m keim exe-verify build/agenten_bundle --json
python -m keim exe-run build/agenten_bundle
python -m keim web-build --cwd examples/agenten_zweige_v78_1_gpu_aware --out build/web --json

35.5 Lesson exercise

  1. Read exe-status and mark supported features.
  2. Create a directory bundle.
  3. Find launcher, manifest and runtime files.
  4. Run exe-verify.
  5. Explain when CPU fallback is used for GPU paths.

35.6 Exam questions

  • Why is a bootstrapper not the same as a full AOT compiler?
  • Why must GPU support be manifest-driven and testable?
  • Why is a directory bundle better for teaching than a single opaque binary?
